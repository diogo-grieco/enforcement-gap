FIX 1 — APLICADO | Severidade: ALTA
Floating-point contamination na classificação tipo_egs
================================================================================

PROBLEMA
A condição original para classificar uma observação como 'completo' era:

    WHEN (LOG(1 + n_autos) * LOG(1 + val_multas)) > 0 THEN 'completo'

Matematicamente o produto é zero se e somente se n_autos = 0 ou val_multas = 0.
Porém floating-point IEEE 754 pode produzir resultados como 2.220446e-16 ao
operar com zeros, fazendo com que observações com enforcement nulo passassem
erroneamente para a categoria 'completo'. O impacto seria silencioso: EGS
calculado sobre denominador virtualmente zero, produzindo valores artificialmente
altos e contaminando rankings.

SOLUÇÃO APLICADA
    CREATE OR REPLACE TABLE project2.analytics.egs_final AS
    SELECT
        geocode_ibge, mun, ano,
        area_km2, n_autos, val_multas,
        CASE
            -- completo: enforcement real documentado
            WHEN n_autos > 0 AND val_multas >= 0.01
                THEN LOG(1 + area_km2) / SQRT(LOG(1 + n_autos) * LOG(1 + val_multas))
            -- gap_absoluto: desmatamento sem qualquer enforcement
            WHEN area_km2 > 0
                THEN LOG(1 + area_km2)
            ELSE 0
        END AS egs,
        CASE
            WHEN n_autos > 0 AND val_multas >= 0.01 THEN 'completo'
            WHEN area_km2 > 0                        THEN 'gap_absoluto'
            ELSE                                          'sem_pressao'
        END AS tipo_egs
    FROM project2.analytics.egs_base;

A condição explícita val_multas >= 0.01 elimina ambiguidade semântica e imuniza
contra floating-point. Qualquer valor abaixo de R$0,01 é tratado como ausência
de enforcement financeiro, independente de representação interna.

RESULTADO PÓS-FIX
Fix 1 em si não alterou a distribuição — caráter preventivo confirmado.
Os números abaixo refletem o pipeline v3 completo (Fix 1 + Fix 8 + Fix 9 aplicados):

FIX 2 — ABERTO | Severidade: MÉDIA
val_multas sem ajuste por inflação — viés direcional no EGS
================================================================================

PROBLEMA
O painel cobre 18 anos (2008–2025). val_multas está em reais nominais.
O IPCA acumulado no período é ~200%: R$100.000 em 2008 equivalem a ~R$300.000
em 2025. Sem deflacionamento, o denominador do EGS subestima sistematicamente
a intensidade de enforcement nos anos mais antigos → EGS inflado para anos
anteriores.

TIPO DE VIÉS
  Direção           Monotônico — anos mais antigos sempre têm EGS artificialmente alto
  Magnitude         Cresce com o horizonte temporal; desprezível em janelas curtas
  Mitigante         Rankings cross-seccionais dentro do mesmo ano são preservados
  Componente exposto Threshold p75 poolado (ver Fix 3)
  É normalização?   Não — é viés direcional, não cancelamento simétrico

SOLUÇÃO PROPOSTA — deflação por IPCA
    -- 1. Tabela auxiliar de deflator IPCA (ano base = 2025)
    CREATE OR REPLACE TABLE project2.staging.ipca_deflator AS
    SELECT * FROM (VALUES
        (2008, 2.973), (2009, 2.687), (2010, 2.477),
        (2011, 2.248), (2012, 2.082), (2013, 1.921),
        (2014, 1.774), (2015, 1.609), (2016, 1.449),
        (2017, 1.384), (2018, 1.330), (2019, 1.280),
        (2020, 1.218), (2021, 1.131), (2022, 1.047),
        (2023, 1.019), (2024, 1.000), (2025, 1.000)
    ) AS t(ano, deflator);

    -- 2. Incorporar deflator no egs_base
    CREATE OR REPLACE TABLE project2.analytics.egs_base_real AS
    SELECT b.*, ROUND(b.val_multas * d.deflator, 2) AS val_multas_real
    FROM project2.analytics.egs_base b
    LEFT JOIN project2.staging.ipca_deflator d USING (ano);

    -- 3. Recalcular egs_final usando val_multas_real no lugar de val_multas

Nota: valores do deflator são aproximados — substituir pelos valores exatos
do IBGE/Sidra (série IPCA acumulado) antes de publicar.

FIX 3 — ABERTO | Severidade: MÉDIA
Threshold p75 poolado — mistura escalas nominais entre anos
================================================================================

PROBLEMA
O qualifying step da persistência completo usa:

    WHERE egs > (SELECT PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY egs)
                 FROM project2.analytics.egs_final
                 WHERE tipo_egs = 'completo')

Com val_multas em valores nominais, anos mais antigos têm EGS sistematicamente
maior. O p75 poolado (0.727) é calibrado numa mistura de escalas, permitindo
que municípios dos anos 2008–2012 ultrapassem o limiar mais facilmente do que
municípios equivalentes em 2020–2025. Pode inflar artificialmente streaks antigos.

SOLUÇÃO A — p75 por ano (recomendada)
    WITH p75_by_year AS (
        SELECT
            ano,
            PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY egs) AS p75_egs
        FROM project2.analytics.egs_final
        WHERE tipo_egs = 'completo'
        GROUP BY ano
    ),
    qualifying AS (
        SELECT e.*
        FROM project2.analytics.egs_final e
        JOIN p75_by_year p USING (ano)
        WHERE e.tipo_egs = 'completo'
          AND e.egs > p.p75_egs
    )
    -- ... resto da query de persistência inalterado

SOLUÇÃO B — combinar com Fix 2
Se Fix 2 for aplicado (deflação), val_multas_real já corrige a escala nominal.
Nesse caso o p75 poolado sobre EGS com valores reais é metodologicamente
defensável. Fix 3 torna-se redundante se Fix 2 for implementado.

FIX 4 — ABERTO | Severidade: BAIXA
Desmatamento autorizado não excluído (PRODES ≠ ilegal)
================================================================================

PROBLEMA
PRODES mede perda de cobertura florestal detectada por satélite — não confirma
ilegalidade. Uma fração do area_km2 pode corresponder a supressão autorizada via
ASV ou Reserva Legal computada no CAR. Municípios com alta atividade agropecuária
legal podem ter EGS elevado não por falha de enforcement, mas por desmatamento
autorizado não subtraído.

Caso específico: Barra do Bugres (MT) — potencialmente alta proporção de
desmatamento legal via AUTEX/DOF. Classificação gap_absoluto é metodologicamente
correta (PRODES detecta, IBAMA não lavra), mas a interpretação muda de impunidade
para autorização. Verificar antes de incluir na narrativa final.

SOLUÇÃO PROPOSTA — cruzamento com SICAR/CAR
    -- Conceitual: subtrair área licenciada do area_km2 antes do EGS
    -- Fonte: SICAR (Sistema Nacional de Cadastro Ambiental Rural)
    --        SFB — autorizações de supressão por município-ano

    CREATE TABLE project2.staging.asv_municipio AS
    SELECT
        geocode_ibge,
        YEAR(data_autorizacao) AS ano,
        SUM(area_autorizada_ha) / 100.0 AS area_autorizada_km2
    FROM sicar.autorizacoes_supressao
    GROUP BY geocode_ibge, YEAR(data_autorizacao);

    -- No egs_base: GREATEST(0, area_km2 - COALESCE(area_autorizada_km2, 0))
    --              como area_km2_ilegal

Nota de dados: SICAR agregado por município-ano não está disponível em série
histórica consistente. Para o MVP, o caveat de interpretação no documento de
resultados é o tratamento adequado.

FIX 5 — ABERTO | Severidade: BAIXA
Enforcement estadual ausente — somente autos federais (IBAMA)
================================================================================

PROBLEMA
O dataset IBAMA captura apenas infrações administrativas federais. Secretarias
estaduais (SEMAS-PA, IDESAM-AM, SEMA-MT, etc.) também emitem autos de infração.
Um município classificado como gap_absoluto pode ter enforcement estadual não
registrado no dataset. O viés é conservador (subestima enforcement), mas pode
gerar falsos positivos para municípios em estados com sistemas estaduais ativos.

  Disponibilidade    SEMAS-PA e MAPA disponibilizam dados parcialmente; sem API nacional
  Efeito no ranking  Conservador — EGS real ≤ EGS calculado para municípios com est. ativo
  Estados expostos   Pará (SEMAS), Mato Grosso (SEMA-MT), Rondônia (SEDAM)
  Tratamento MVP     Documentar caveat; enquadrar como 'enforcement federal mínimo'

SOLUÇÃO DE LONGO PRAZO
    CREATE TABLE project2.staging.autos_estaduais (
        geocode_ibge   VARCHAR,
        ano            INTEGER,
        uf             VARCHAR(2),
        n_autos_est    INTEGER,
        val_multas_est DECIMAL(18,2),
        fonte          VARCHAR   -- 'SEMAS-PA', 'SEMA-MT', etc.
    );

    -- Combinar com IBAMA no egs_base via COALESCE nos dois denominadores

FIX 6 — MVP FUTURO | Severidade: ALTA
Extensão biomas: spatial join para Cerrado / Caatinga / Mata Atlântica
================================================================================

PROBLEMA
O pipeline atual usa join tabular por geocode_ibge entre PRODES Amazônia e
IBAMA infrações. Fora da Amazônia Legal dois problemas bloqueiam a extensão:

  Problema 1 — Incompatibilidade de unidade: PRODES Cerrado/Caatinga organiza
  dados por geometria de bioma (shapefiles), não por geocode municipal.
  O join tabular quebra.

  Problema 2 — Heterogeneidade metodológica: cada produto PRODES usa área mínima
  de detecção, definições de classe e períodos distintos. Comparação direta de
  km² entre biomas é metodologicamente indefensável.

SOLUÇÃO 1 — Spatial join via coordenadas GPS do IBAMA
Todo auto de infração IBAMA contém NUM_LATITUDE_AUTO e NUM_LONGITUDE_AUTO.
Substituir o geocode join por spatial join com polígonos de bioma habilita
análise cross-bioma sem depender de matching administrativo.

    INSTALL spatial; LOAD spatial;

    -- Pontos a partir das coordenadas IBAMA
    CREATE TABLE project2.staging.ibama_geo AS
    SELECT *, ST_Point(NUM_LONGITUDE_AUTO, NUM_LATITUDE_AUTO) AS geom_auto
    FROM project2.staging.ibama_raw
    WHERE NUM_LATITUDE_AUTO IS NOT NULL AND NUM_LONGITUDE_AUTO IS NOT NULL;

    -- Spatial join com polígonos de bioma
    CREATE TABLE project2.staging.ibama_com_bioma AS
    SELECT i.*, b.nome_bioma
    FROM project2.staging.ibama_geo i
    JOIN project2.staging.biomas b ON ST_Within(i.geom_auto, b.geom);

SOLUÇÃO 2 — Normalização intra-bioma antes do EGS
Substituir área absoluta por percentil intra-bioma (PERCENT_RANK particionado
por nome_bioma e ano) para eliminar incompatibilidade de escala cross-bioma.

Shapefiles necessários: IBGE Biomas 2019 (ibge.gov.br/geociencias),
PRODES Cerrado e Caatinga (terrabrasilis.dpi.inpe.br).

FIX 7 — FECHADO | Severidade: MÉDIA
Same-year join — lag temporal entre PRODES e IBAMA
================================================================================

PROBLEMA ORIGINAL
O pipeline assume que desmatamento detectado pelo PRODES no ano X e enforcement
registrado pelo IBAMA no ano X correspondem ao mesmo evento. A questão era se
um join com defasagem de 1 ano (t+1) seria mais adequado.

ANÁLISE EMPÍRICA — 4 sub-análises sobre 58.051 registros
(possível após Fix 8 — base completa com 0% de NULLs em DAT_HORA_AUTO_INFRACAO)

    pct_match_t   = 68.8%   -- autos IBAMA que encontram PRODES no mesmo ano
    pct_match_t1  = 65.2%   -- autos IBAMA que encontram PRODES no ano seguinte
    pct_ambos     = 64.4%   -- match em t E t+1 (sobreposição)
    pct_nenhum    = 30.5%   -- sem match em nenhum dos dois anos

    Distribuição mensal: pico em setembro–outubro (estação seca, pressão máxima)
    Sem concentração em janeiro–março que indicaria resposta ao ano anterior.

    Análise de sensibilidade: 1.033 de 5.966 gap_absoluto (17.4%) mudariam
    de categoria com join t+1. Municípios com streak >= 3 anos são robustos.

DECISÃO — Same-year join confirmado e mantido
  (1) match t=0 supera match t+1 em 3.6pp sobre a base completa
  (2) distribuição mensal não mostra padrão de resposta ao ano anterior
  (3) casos com streak >= 3 anos são robustos ao viés de lag (apenas 17.4%
      dos gap_absoluto mudariam, todos casos marginais sem streak persistente)

TRADE-OFFS DAS ALTERNATIVAS
  Same-year join [adotado]  Viés residual em ~17.4% gap_absoluto — mitigado pela persistência
  Rolling window            Risco de double-counting — infrações contadas múltiplas vezes
  Cumulative stock          Perde dimensão temporal — não detecta melhora/piora

LIMITAÇÃO RESIDUAL DOCUMENTADA
Municípios com enforcement atrasado (X+1 ou X+2) geram dois sinais artificiais:
gap_absoluto no ano X e enforcement sem pressão no X+1. A lógica de persistência
absorve parte do ruído. Documentado no README como limitação técnica intermediária.

FIX 8 — APLICADO | Severidade: CRÍTICA
Coluna de data errada — DT_FATO_INFRACIONAL com 69% de NULLs
================================================================================

PROBLEMA
O pipeline v1 extraía o ano de cada auto IBAMA da coluna DT_FATO_INFRACIONAL
(data do fato infracional). Análise exploratória revelou 69% de NULLs no dataset
filtrado (Flora + Desmatamento + Lavrado): 40.409 de 58.051 registros perdiam
o ano e eram descartados silenciosamente. Resultado: 57.7% gap_absoluto quando
o valor correto é 41.2% — diferença de 16.5pp e 2.400 observações.
O erro era estrutural e afetava todos os rankings.

DIAGNÓSTICO
    null_dt_fato_infracional  = 40.409  (69.6% dos 58.051 registros filtrados)
    null_dat_hora_auto        =      0  (0% — zero NULLs)

    Correlação: completude de DT_FATO_INFRACIONAL correlaciona com valor da multa
    val_multa ~ R$7k     → 2–7% de completude
    val_multa ~ R$300k+  → 50–70% de completude
    Hipótese: registros de alto impacto recebem tratamento mais cuidadoso
    Consequência v1: pipeline capturava preferencialmente infrações de alto valor

SOLUÇÃO APLICADA
    CREATE OR REPLACE TABLE project2.marts.ibama_clean AS
    SELECT
        COD_MUNICIPIO AS geocode_ibge,
        UF AS uf,
        -- DAT_HORA_AUTO_INFRACAO: data de lavratura formal do auto
        -- Zero NULLs no dataset completo. Substitui DT_FATO_INFRACIONAL (69% NULL).
        EXTRACT(YEAR FROM CAST(DAT_HORA_AUTO_INFRACAO AS DATE)) AS ano,
        CAST(REPLACE(VAL_AUTO_INFRACAO, ',', '.') AS DOUBLE) AS val_multa
    FROM project2.staging.ibama_raw
    WHERE
        TIPO_INFRACAO             = 'Flora'
        AND INFRACAO_AREA         = 'Desmatamento'
        AND SIT_CANCELADO         = 'N'
        AND DES_STATUS_FORMULARIO = 'Lavrado';

TRADE-OFF DOCUMENTADO
A data de lavratura pode diferir da data do fato por dias a meses — especialmente
em municípios remotos onde a lavratura ocorre após o deslocamento do inspetor.
Em casos limítrofes de virada de ano, um auto lavrado em janeiro X pode referir-se
a desmatamento de dezembro X-1, gerando desalinhamento de 1 ano no join com PRODES.
Fix 7 quantifica: 17.4% dos gap_absoluto mudariam com join t+1.
Municípios com streak >= 3 anos são robustos a essa incerteza.

FIX 9 — APLICADO | Severidade: MÉDIA
Filtro IBAMA: 1 caso → 3 casos (cobertura 2008–2012)
================================================================================

PROBLEMA
O filtro em 02_marts.sql (ibama_clean) usa condição única:

    TIPO_INFRACAO = 'Flora' AND INFRACAO_AREA = 'Desmatamento'

INFRACAO_AREA não era campo obrigatório no sistema IBAMA em 2008–2012. Registros
do período têm NA em INFRACAO_AREA e/ou TIPO_INFRACAO mas carregam COD_INFRACAO
explícito de desmatamento. O filtro original excluía silenciosamente 2.656
registros válidos desse período.

ANÁLISE EMPÍRICA (R exploration script, 2026-05-03)
    count(TIPO_INFRACAO):   Flora 125k | Fauna 51k | NA 12k
    count(INFRACAO_AREA):   NA 110k | Desmatamento 102k
                            NAs concentrados em 2008–2012 (campo não obrigatório)
    count(COD_INFRACAO):    356 códigos distintos; 6 específicos de desmatamento

    Case 1 — Flora + Desmatamento (ambos presentes):      58.051 registros
    Case 2 — Flora + NA área + código de desmatamento:     2.129 registros
    Case 3 — NA tipo + Desmatamento:                         527 registros
    Total após expansão:                                  60.707 registros

CODIGOS_DESMATAMENTO (6 de 356 identificados por leitura das descrições):
    409907, 409901, 452001, 430001, 431003, 468001
    409999 excluído: genérico "Não Classificada-Móvel" (77.872 registros);
    registros com INFRACAO_AREA = Desmatamento já em Cases 1/3; 14.710 restantes
    têm NA em ambos os campos — sem sinal recuperável.

"DESMATAMENTO E QUEIMADA" — investigado e excluído
    2.051 registros válidos (SIT_CANCELADO=N, Lavrado)
    Flora subset (1.606): 1.579 são 409999 — mesmo código genérico excluído
    26 são 422006 (Sisflora, comércio de madeira) — fora do escopo
    Conclusão: dominado por 409999; exclusão consistente com filtro principal

SOLUÇÃO — atualizar WHERE em 02_marts.sql (ibama_clean)
    WHERE
        SIT_CANCELADO         = 'N'
        AND DES_STATUS_FORMULARIO = 'Lavrado'
        AND (
            -- Case 1: Flora + Desmatamento (58.051)
            (TIPO_INFRACAO = 'Flora' AND INFRACAO_AREA = 'Desmatamento')
            -- Case 2: Flora + NA área + código explícito (2.129) — 2008-2012
            OR (TIPO_INFRACAO = 'Flora' AND INFRACAO_AREA IS NULL
                AND COD_INFRACAO IN (
                    '409907','409901','452001','430001','431003','468001'))
            -- Case 3: NA tipo + Desmatamento (527) — mesmo padrão 2008-2012
            OR (TIPO_INFRACAO IS NULL AND INFRACAO_AREA = 'Desmatamento')
        );

RESULTADO APÓS APLICAÇÃO (2026-05-04)
    Filtro v1 (caso único):    58.051 registros
    Filtro v2 (3 casos):       60.707 registros (+2.656, +4.6%)

    Impacto no egs_final (pipeline v3):
    completo     +3.226  (4.667 → 7.893, +69%)
    gap_absoluto -2.182  (5.966 → 3.784, -37%)
    sem_pressao  -1.044  (3.857 → 2.813, -27%)
    p75 EGS      -0.138  (0.7267 → 0.5891) — pool completo cresceu

    Validação: municípios do topo gap_absoluto (Governador Luiz Rocha,
    Fortuna, São Domingos do Maranhão) mantêm perfil esperado.
    Lista completo inclui corretamente Itaituba, Altamira, Novo Repartimento.
    Resultados credíveis — fix encerrado.

    Nota: 1.044 pares com area_km2=0 migraram de sem_pressao para completo.
    Interpretação: IBAMA autuou desmatamento abaixo do limite de detecção PRODES
    (< 1 km²). EGS = 0 nesses casos (numerador LOG(1+0) = 0). Documentar como
    limitação no apêndice metodológico.
