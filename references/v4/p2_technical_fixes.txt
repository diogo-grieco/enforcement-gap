FIX 1 — APLICADO | Severidade: ALTA
Floating-point contamination na classificação tipo_egs
================================================================================

PROBLEMA
A condição original para classificar uma observação como 'completo' era:

    WHEN (LOG(1 + n_autos) * LOG(1 + val_multas)) > 0 THEN 'completo'

Matematicamente o produto é zero se e somente se n_autos = 0 ou val_multas = 0.
Porém floating-point IEEE 754 pode produzir resultados como 2.220446e-16 ao
operar com zeros, fazendo com que observações com enforcement nulo passassem
erroneamente para a categoria 'completo'. O impacto seria silencioso: EGS
calculado sobre denominador virtualmente zero, produzindo valores artificialmente
altos e contaminando rankings.

SOLUÇÃO APLICADA (histórica — ver Fix 11 para a versão atual da classificação)
    CASE
        WHEN n_autos > 0 AND val_multas >= 0.01
            THEN LOG(1 + area_km2) / SQRT(LOG(1 + n_autos) * LOG(1 + val_multas))
        WHEN area_km2 > 0
            THEN LOG(1 + area_km2)
        ELSE 0
    END AS egs

A condição explícita val_multas >= 0.01 elimina ambiguidade semântica e imuniza
contra floating-point. Esse threshold permanece em uso no pipeline atual
(03_analytics.sql); o que mudou desde então é o limite de área que separa
gap_absoluto de sem_pressao (Fix 11) e o valor de egs para sem_pressao (Fix 13).

FIX 2 — APLICADO | Severidade: MÉDIA
val_multas sem ajuste por inflação — viés direcional no EGS
================================================================================

PROBLEMA
O painel cobre 18 anos (2008–2025). val_multas está em reais nominais.
Sem deflacionamento, o denominador do EGS subestima sistematicamente a
intensidade de enforcement nos anos mais antigos → EGS inflado para anos
anteriores. Ver análise original de viés (mantida por referência):

  Direção            Monotônico — anos mais antigos sempre têm EGS artificialmente alto
  Magnitude          Cresce com o horizonte temporal
  Mitigante          Rankings cross-seccionais dentro do mesmo ano são preservados
  Componente exposto Threshold p75 poolado (ver Fix 3)

SOLUÇÃO APLICADA (2026-07-10 — substitui a proposta v3 com valores aproximados)

    -- 1. ipca_deflator: valores reais do IBGE/Sidra t.1737 v.2266,
    --    Brasil, jan/2008-dez/2025, download 2026-07-10 (01_staging.sql)
    --    Base 2025 = média dos índices mensais do ano (lavraturas se
    --    distribuem pelo ano; pico set-out). Formato largo do Sidra
    --    tratado via UNPIVOT + regex contra vazamento de rodapé.
    CREATE OR REPLACE TABLE project2.staging.ipca_deflator AS
    WITH wide AS (
        SELECT * FROM read_csv(
            'data_ipca/sidra_1737_v2266_ipca_indice_200801_202512_2026_07_10.csv',
            delim = ';', skip = 3, header = true,
            all_varchar = true, null_padding = true, ignore_errors = true,
            parallel = false)
    ),
    long AS (
        UNPIVOT wide ON COLUMNS('\d{4}$') INTO NAME mes VALUE indice
    ),
    anual AS (
        SELECT CAST(regexp_extract(mes, '(\d{4})$', 1) AS INTEGER) AS ano,
               AVG(CAST(REPLACE(indice, ',', '.') AS DOUBLE))      AS indice_medio
        FROM long
        WHERE regexp_matches(indice, '^\d+(,\d+)?$')
        GROUP BY ano
    )
    SELECT ano,
           (SELECT indice_medio FROM anual WHERE ano = 2025) / indice_medio AS deflator
    FROM anual
    ORDER BY ano;

    -- 2. egs_base: val_multas_nominal preservado + val_multas deflacionado
    --    (03_analytics.sql) — deflator é por ano, multiplicar o agregado
    --    anual é equivalente a deflacionar cada auto individualmente
    COALESCE(SUM(i.val_multa), 0)                AS val_multas_nominal,
    COALESCE(SUM(i.val_multa), 0) * d.deflator   AS val_multas

    -- egs_final e p75 usam val_multas (deflacionado), não val_multas_nominal

TRADE-OFF / PENDÊNCIA RESIDUAL
val_multas_nominal é mantido na tabela egs_base para fins de auditoria — não
usado em nenhum cálculo downstream. Nenhuma pendência conhecida neste fix;
municipios_ref (Fix 12) é independente e não bloqueia este.

INCONSISTÊNCIA A CORRIGIR NO PRÓPRIO ARQUIVO
O cabeçalho de 03_analytics.sql ainda lista este fix como "PENDENTE (Fix 2/3):
deflacionar val_multa..." — comentário desatualizado; o corpo do arquivo já
aplica a deflação. Corrigir o comentário na próxima revisão do SQL.

FIX 3 — FECHADO | Severidade: MÉDIA
Threshold p75 poolado — mistura escalas nominais entre anos
================================================================================

PROBLEMA ORIGINAL
O p75 poolado (calculado sobre todos os anos juntos) era calibrado numa
mistura de escalas nominais, permitindo que municípios de anos antigos
(val_multa nominal baixo em termos reais) ultrapassassem o limiar mais
facilmente que municípios equivalentes em anos recentes.

RESOLUÇÃO — Solução B, não Solução A
A v3 deste documento propunha duas soluções: (A) p75 calculado por ano,
ou (B) resolver via deflação (Fix 2), tornando o p75 poolado defensável.
Fix 2 foi aplicado — val_multas usado no cálculo do EGS já está em reais
de 2025. Solução A (p75 por ano) não foi implementada e não é necessária
enquanto o EGS for calculado sobre valores deflacionados.

MUDANÇA ADICIONAL — p75 hardcoded → dinâmico
Independente deste fix, o p75 deixou de ser um valor fixo (0.727, citado
na v3 da session reference) e passou a ser calculado dinamicamente via CTE
em cada execução de 03_analytics.sql:

    WITH p75 AS (
        SELECT PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY egs) AS p75_egs
        FROM project2.analytics.egs_final
        WHERE tipo_egs = 'completo'
    )

Isso elimina o risco de drift documentado na v3 (§ "p75 hardcoded vs. dinâmico")
— o valor sempre reflete a distribuição atual dos dados. O valor numérico do
p75 sob o pipeline atual (materialidade + deflator) ainda não está registrado
neste documento — rodar o check "p75 de referência" em 03_analytics.sql antes
de citar em narrativa.

STATUS: reavaliar se p75 por ano (Solução A) se torna necessário caso o
pipeline volte a usar valores nominais em algum momento.

FIX 4 — ABERTO | Severidade: BAIXA
Desmatamento autorizado não excluído (PRODES ≠ ilegal)
================================================================================

PROBLEMA
PRODES mede perda de cobertura florestal detectada por satélite — não confirma
ilegalidade. Uma fração do area_km2 pode corresponder a supressão autorizada via
ASV ou Reserva Legal computada no CAR.

Caso específico: Barra do Bugres (MT) — identificado (v3) como candidato a alta
proporção de desmatamento legal via AUTEX/DOF. NENHUMA verificação externa foi
feita entre a v3 (2026-05-07) e o pipeline atual (2026-07-10) — não há menção
a Barra do Bugres em nenhum arquivo SQL ou R atualizado. Classificação
gap_absoluto é metodologicamente correta (PRODES detecta, IBAMA não lavra),
mas a interpretação muda de impunidade para autorização caso confirmado.

SOLUÇÃO PROPOSTA — cruzamento com SICAR/CAR (inalterada desde v3)
    CREATE TABLE project2.staging.asv_municipio AS
    SELECT
        geocode_ibge,
        YEAR(data_autorizacao) AS ano,
        SUM(area_autorizada_ha) / 100.0 AS area_autorizada_km2
    FROM sicar.autorizacoes_supressao
    GROUP BY geocode_ibge, YEAR(data_autorizacao);

Nota de dados: SICAR agregado por município-ano não está disponível em série
histórica consistente. Para o MVP, o caveat de interpretação no documento de
resultados é o tratamento adequado — mas o caveat ainda não foi verificado.

  Disponibilidade    SEMAS-PA e MAPA disponibilizam dados parcialmente; sem API nacional
  Efeito no ranking  Conservador — EGS real ≤ EGS calculado para municípios com est. ativo
  Estados expostos   Pará (SEMAS), Mato Grosso (SEMA-MT), Rondônia (SEDAM)
  Tratamento MVP     Documentar caveat; enquadrar como 'enforcement federal mínimo'

FIX 10 — APLICADO | Severidade: MÉDIA (NOVO em v4)
priority_score = 0 quando max_streak = 1
================================================================================

PROBLEMA (sinalizado na v3 da session reference, nunca registrado aqui)
priority_score = LOG(max_streak) * LOG(1 + total_desmatado_km2). Quando
max_streak = 1, LOG(1) = 0, zerando o score independente do volume de
desmatamento — um município com streak=1 e 500 km² desmatados desapareceria
silenciosamente do ranking.

SOLUÇÃO APLICADA (03_analytics.sql, 2026-07-10)
Não foi a correção proposta na v3 (LOG(streak+1)). Em vez disso, o filtro de
persistência roda ANTES da agregação que calcula priority_score:

    -- streaks CTE não filtra por streak_length
    SELECT geocode_ibge, mun, ano - rn AS streak_group,
           COUNT(*) AS streak_length, ...
    FROM qualifying
    GROUP BY geocode_ibge, mun, ano - rn

    -- filtro aplicado ANTES do MAX()/priority_score, não depois
    SELECT geocode_ibge, mun,
           MAX(streak_length) AS max_streak,
           ...
           ROUND(LOG(MAX(streak_length)) * LOG(1 + SUM(area_no_streak)), 3) AS priority_score
    FROM streaks
    WHERE streak_length >= 3
    GROUP BY geocode_ibge, mun

Como só streaks com streak_length >= 3 entram na agregação, MAX(streak_length)
nunca é 1 — LOG(1)=0 nunca ocorre em priority_score. Comentário no SQL trata
isso como decisão de design: "streak 1-2 não é zerado pelo LOG, é excluído por
regra de persistência (1 ciclo eleitoral + margem). Design, não bug."

TRADE-OFF
Resolve o bug de forma diferente da sugerida na v3. Não há mais necessidade de
LOG(streak+1) porque municípios com streak 1-2 já são excluídos do ranking por
regra de negócio (persistência mínima de 3 anos) antes de chegar ao cálculo do
score — mas isso significa que municípios com streak=1-2 e área expressiva
continuam invisíveis nos rankings de persistência, só que por exclusão
deliberada em vez de por artefato aritmético. Se a intenção for capturar esses
casos, é necessário um ranking separado (sem filtro de persistência) — não
implementado.

FIX 11 — APLICADO | Severidade: BAIXA (NOVO em v4)
tipo_egs: limite de materialidade ambíguo (>0 vs >=1 km²)
================================================================================

PROBLEMA
A v3 da session reference era internamente inconsistente: §4.4 documentava
"Threshold area_km2 >= 1: limite de detecção do PRODES" como decisão locked,
mas a tabela de classificação em §4.7 usava area_km2 > 0 para diferenciar
gap_absoluto de sem_pressao — sem aplicar o limite de 1 km² mencionado em §4.4.

SOLUÇÃO APLICADA (03_analytics.sql, 2026-07-10)
Classificação agora aplica >=1 km² consistentemente:

    CASE
        WHEN area_km2 < 1          THEN 'sem_pressao'
        WHEN val_multas < 0.01     THEN 'gap_absoluto'
        ELSE                            'completo'
    END AS tipo_egs

Documentado explicitamente no cabeçalho do arquivo como decisão (a)
MATERIALIDADE: "área >= 1 km² em classificação e rankings — ordem de grandeza
acima da área mínima de mapeamento do PRODES (6,25 ha), elimina desmatamento
residual sem relevância de priorização."

IMPACTO
gap_absoluto sob o critério antigo (>0 km², pipeline v3) = 3.784.
gap_absoluto sob o critério atual (>=1 km², pipeline v4) = 3.063 (checkpoint
cruzado R/SQL, ver exploring_script.R N_GAP_ABSOLUTO e comentário em
03_analytics.sql). Diferença de 721 município-anos que tinham entre 0 e 1 km²
desmatados sem enforcement — agora corretamente tratados como sem_pressao
material em vez de gap de enforcement.

PROBLEMA
Na v3 (§4.7), sem_pressao tinha egs = 0 (mesma escala numérica que completo e
gap_absoluto). No pipeline atual, sem_pressao tem egs = NULL:

    CASE
        WHEN area_km2 >= 1 AND val_multas >= 0.01
            THEN LOG(1 + area_km2) / SQRT(LOG(1 + n_autos) * LOG(1 + val_multas))
        WHEN area_km2 >= 1
            THEN LOG(1 + area_km2)
        ELSE NULL   -- sem pressão material
    END AS egs

Essa mudança não aparece em nenhum changelog da session reference nem deste
documento até agora — foi descoberta por auditoria de código, não por registro
do autor.

AVALIAÇÃO
Mudança faz sentido semanticamente: egs=0 sugeria "pressão mínima mas presente
e bem respondida", quando na verdade sem_pressao significa "não há pressão
material para avaliar" — categorias diferentes que não deveriam compartilhar
um valor numérico comparável (ex. AVG(egs) por ano incluindo sem_pressao=0
sub-estimaria o EGS médio real de forma enganosa). NULL é semanticamente mais
correto e evita esse viés em agregações. resumo_anual (04_export.sql) já
explora isso corretamente: avg_egs_completo usa CASE WHEN tipo_egs='completo'
THEN egs END, que ignora sem_pressao de qualquer forma — então o impacto
prático da mudança é pequeno, mas deveria ter sido registrado quando feita.

AÇÃO
Nenhuma correção de código necessária. Ação é apenas documental: registrar a
mudança (feito neste fix) e adicionar entrada correspondente na próxima
atualização da session reference (feito na v4, ver mudança em §4.7).

FIX 14 — APLICADO | Severidade: MÉDIA (NOVO em v5)
Paths hardcoded — portabilidade GitHub/Zenodo
================================================================================

PROBLEMA
Ao rodar o pipeline pela primeira vez no DBeaver (2026-07-12), os 4
read_csv/read_json_auto de 01_staging.sql falharam com "No files found" —
os paths relativos ("data_prodes/...") são resolvidos contra o diretório de
trabalho do processo, que no DBeaver não é a raiz do projeto. Solução
imediata do autor: hardcode de path absoluto pessoal
(C:/Users/diogo/projects/project2/...) direto nos 4 lugares. Funciona
localmente, mas não é publicável — quebra para qualquer outra máquina,
incluindo o próprio autor em outro computador, e expõe estrutura de pastas
pessoal no código versionado.

SOLUÇÃO APLICADA
Ponto único de configuração via variável de sessão do DuckDB (SET VARIABLE /
getvariable, recurso nativo, documentado em duckdb.org/docs/current/sql/
statements/set_variable), no topo de 01_staging.sql:

    SET VARIABLE data_root = 'C:/Users/diogo/projects/project2';  -- editar

    CREATE OR REPLACE TABLE project2.staging.prodes_raw AS
    SELECT * FROM read_csv(
        getvariable('data_root') || '/data_prodes/terrabrasilis_legal_amazon_*.csv',
        ...);

Funciona igual em DBeaver, CLI do DuckDB e R (pacote duckdb/DBI) — não
depende do diretório de trabalho de nenhum cliente. Quem clonar o repositório
edita uma linha, não os 4 lugares onde os arquivos são lidos.

RECOMENDAÇÃO PENDENTE (não aplicada — decisão do autor)
Para GitHub/Zenodo: não versionar as pastas de dados brutos (data_prodes/,
data_ibama/, data_ibge/, data_ipca/) — grandes e de download manual.
.gitignore nelas, documentar fonte/instrução de download no README (já
existem como comentário em cada tabela do 01_staging.sql, só precisam ser
consolidados lá).
